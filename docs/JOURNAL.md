# Журнал выводов

## 2026-10-17 — прямые зависимости Windows-модуля

Гипотеза: обычные debug-модули из выпуска № 22 требуют отдельные DLL MinGW
runtime, а полный `-static` может нарушить требование единой `libcrypto`.

Проверка: PE-импорты всех трёх скачанных модулей просмотрены напрямую. Везде
есть `libwinpthread-1.dll` и архитектурная `libcrypto-3*.dll`; на x86 есть
также `libgcc_s_dw2-1.dll`. `libdl.dll` ни один из них не импортирует.
Страница пакета MSYS2 winpthreads подтверждает наличие `libwinpthread.a` и
лицензию MIT AND BSD-3-Clause, а не LGPL.

Вывод: из прямых импортов можно убрать MinGW runtime, но без динамической
`libcrypto` провайдер не должен оставаться: приложение и провайдер используют
общие объекты OpenSSL. Проверка публикации должна требовать этот импорт и
отклонять прочие несистемные DLL.

Повторная проверка: release-архивы выпуска № 23 проверены по `SHA256SUMS`.
PE-импорты каждой Windows DLL содержат лишь системные DLL и архитектурную
`libcrypto`; прямых импортов `libwinpthread` и `libgcc` нет. Все три release
модуля загрузились на соответствующих GitHub runners; три прямых unit-теста
прошли в отдельных debug-сборках. Официальный пакет OpenSSL MSYS2 UCRT64
3.6.5-1 скачан и сверен по SHA-256 со страницы пакета. Его `libcrypto` имеет
лишь системные Windows-импорты, а `libssl` импортирует эту же `libcrypto` и
системные DLL. Это отдельно проверено для UCRT64 x64; импортные таблицы
пакетов OpenSSL для x86 и ARM64 отдельно не проверялись.

## 2026-10-17 — доступные среды MSYS2 для Windows x86 и ARM64

Гипотеза: MSYS2 предоставляет готовые пакеты OpenSSL и инструменты
сборки для обеих дополнительных архитектур, а GitHub предоставляет
ARM64 runner.

Проверка: каталог пакетов MSYS2 показывает OpenSSL, Meson, Ninja,
pkgconf и p11-kit для MINGW32/i686 и CLANGARM64/aarch64. Для ARM64
есть пакет Clang, для i686 — GCC. Документация GitHub перечисляет
`windows-11-arm`; `setup-msys2` принимает `MINGW32` и `CLANGARM64`.

Вывод: для x86 можно собирать на x64 Windows runner в MINGW32, для ARM64
на ARM64 Windows runner в CLANGARM64. MSYS2 предупреждает об устаревании
MINGW32 без прямой замены, поэтому доступность этой среды нужно проверять
каждым запуском CI.

Повторная проверка: GitHub runners собрали обе новые цели; три прямых
unit-теста, загрузка модуля через OpenSSL и проверка архива прошли на
каждой. В скачанных DLL PE Machine равен x86, x64 и ARM64 по целям;
семь архивов выпуска № 22 прошли `SHA256SUMS`.


## 2026-10-17 — повторный PIN и завершение portable SoftHSM

Решение владельца: не блокировать `CKF_USER_PIN_FINAL_TRY` и не запоминать
ранее отвергнутый PIN в провайдере. Отказ при `CKF_USER_PIN_LOCKED` оставить.
При неверном PIN попытки могут исчерпаться и токен может заблокироваться;
этот выбор теперь делает вызывающее приложение.

Проверка: архив portable SoftHSM `.76` для Linux x64 прошёл проверку
`SHA256SUMS`. С ним готовый провайдер выпуска № 20 и новая локальная
сборка создают CSR с заводским PIN и завершаются с кодом 0 без
`no-deinit`; подпись CSR корректна. На двух отдельных токенах одинаковый
неверный PIN был подан дважды в одном процессе: выпуск № 20 дошёл до
`C_Login` один раз и затем заблокировал повтор в провайдере, новая
сборка дошла до `C_Login` дважды. Прямой unit-тест подтвердил поведение
флагов PIN. Аппаратный Рутокен не проверялся.

Вывод: исправление закрытия сессии в portable SoftHSM `.76` устранило
ранее наблюдавшееся падение в проверенном сценарии Linux. Повторный
неверный PIN теперь обрабатывает сам PKCS #11 модуль.

Повторная проверка: опубликованный Linux x86_64 модуль выпуска № 21
также завершил создание CSR с кодом 0 без `no-deinit` и дважды вызвал
`C_Login` при двух подачах неверного PIN в одном процессе. Пять архивов
совпали с `SHA256SUMS`.


## 2026-10-17 — флаг смены заводского PIN и вход через провайдер

Гипотеза: ранний отказ `check_pin_flags_ok` по
`CKF_USER_PIN_TO_BE_CHANGED` мешает входу с заводским PIN, который
PKCS #11 модуль принимает в `C_Login`.

Проверка: создан отдельный токен portable SoftHSM с
`FAKE_RUTOKEN_ECP = true`, заводскими PIN и ключом EC P-256. Ранее
выпущенный провайдер не создал CSR и вернул код 1; исправленный провайдер
создал CSR, прошедший проверку подписи, и вернул код 0. В обоих запусках
задан `no-deinit` из-за отдельной проблемы закрытия сессии portable SoftHSM.
На самом Рутокене этот патч не проверялся.

Вывод: `CKF_USER_PIN_TO_BE_CHANGED` нельзя интерпретировать как безусловный
отказ от `C_Login`. Проверку `CKF_USER_PIN_FINAL_TRY` и
`CKF_USER_PIN_LOCKED` оставили без изменения; это отдельные ранние блокировки.

Повторная проверка: модуль Linux x86_64 из опубликованного выпуска № 20
создал CSR с заводским PIN и завершился с кодом 0; подпись CSR проверена.


## 2026-10-16 — целевая версия macOS в готовом модуле

Гипотеза: использование готового OpenSSL из conda-forge с минимумом macOS
11.0 делает и собранный провайдер совместимым с macOS 11.0.

Проверка: в выпущенных для Intel и ARM64 модулях № 18 значение `minos` в
`LC_BUILD_VERSION` равно 15.0 — версии GitHub runner. У библиотек OpenSSL
из conda-forge и universal SoftHSM значение равно 11.0.

Вывод: переменная `MACOSX_DEPLOYMENT_TARGET` должна задаваться до запуска
Meson. Проверка архива должна читать фактическое поле `minos`, поскольку
одна переменная сборки не подтверждает свойство готового файла.

Повторная проверка: в обоих скачанных модулях выпуска № 19 поле `minos`
равно 11.0, а GitHub runner macOS 15 успешно загрузил их через OpenSSL.
Это подтверждает целевую версию готовых файлов, но не заменяет запуск на
самой macOS 11.

## 2026-10-16 — путь сборочного агента в LC_RPATH macOS

Гипотеза: переход на conda-forge install name `@rpath/libcrypto.3.dylib`
сам по себе устраняет пути сборочной машины из готового модуля.

Проверка: модули ARM64 и Intel из выпуска № 16 действительно импортируют
`@rpath/libcrypto.3.dylib`, но оба содержат `LC_RPATH` с временным каталогом
OpenSSL на GitHub runner.

Вывод: при упаковке нужно заменить временный `LC_RPATH` на относительный
`@loader_path/..` и переподписать изменённый модуль. Проверка архива должна
фиксировать и новый путь, и отсутствие временного.

## 2026-10-16 — pkg-config в архиве conda-forge OpenSSL

Гипотеза: pkg-config файлы готового пакета указывают на каталог распаковки.

Проверка: в пакетах OpenSSL 3.6.5 для обеих архитектур переменная `prefix`
сохраняет путь сборочной среды conda-forge. После распаковки без обработки
Meson искал бы заголовки и библиотеки по отсутствующему пути.

Вывод: скрипт установки заменяет `prefix` на каталог распаковки и проверяет
его через `pkg-config` до сборки. Сами dylib используют `@rpath` и не требуют
изменения install name при извлечении.

## 2026-10-16 — SHA в Windows BUILD-INFO

Гипотеза: `git rev-parse HEAD` доступен внутри MSYS2 shell при упаковке.

Проверка: Windows архив выпуска № 14 содержит пустое поле `Git commit`,
хотя опубликован с верным тегом на SHA. Командная подстановка внутри heredoc
не привела к остановке `set -e`.

Вывод: workflow должен передавать штатный `GITHUB_SHA`, а скрипт упаковки и
верификатор — проверять наличие корректного SHA в метаданных.

## 2026-10-16 — макрос interface из Windows SDK

Гипотеза: подключение `<windows.h>` не меняет идентификаторы в коде
загрузчика провайдера.

Проверка: MinGW скомпилировал остальные объекты, но в `interface.c`
появилась ошибка на поле `interface`: Windows SDK определил одноимённый
макрос. Следующие ошибки `OPENSSL_free` были следствием его подстановки.

Вывод: после подключения Windows SDK нужен `#undef interface`.

## 2026-10-16 — pthread типы в публичном заголовке провайдера

Гипотеза: заголовок `provider.h` получает определения `pthread_mutex_t` и
`pthread_rwlock_t` косвенно через другие заголовки на всех платформах.

Проверка: компиляция Windows UCRT64 после настройки pkg-config завершилась
ошибками «unknown type name» для обоих типов в `util.h`, который включается
из `provider.h`.

Вывод: `util.h` должен самостоятельно подключать `<pthread.h>`. Владелец
предоставил проверенный рецепт Windows-сборки, который также подтверждает,
что `endian.h` на MinGW должен миновать GNU-ветку с отсутствующим
`byteswap.h` и использовать fallback-определения.

## 2026-10-16 — поиск proxy DLL на Windows

Гипотеза: `pkg-config --exists p11-kit-1` работает в MSYS2 UCRT64 так же,
как на Linux и macOS.

Проверка: третий Windows job установил пакеты и сохранил OpenSSL в кэш, но
на первой команде сборочного шага `pkg-config --exists p11-kit-1` завершился
с кодом 1.

Вывод: архив пакета MSYS2 проверен отдельно. В UCRT64 есть
`p11-kit-1.pc` и `p11-kit-trust.dll`, но нет `p11-kit-proxy.dll`;
предположение о Windows proxy было неверным. Для прямой проверки загрузки
использовать `p11-kit-trust.dll` и явный путь к UCRT64 pkg-config файлам.

## 2026-10-16 — кэш пакета MSYS2 и порядок установки

Гипотеза: пакет OpenSSL появится в pacman cache после отдельной установки,
если перед ней `setup-msys2` уже установил сборочные инструменты.

Проверка: первый Windows job показал, что Meson установил OpenSSL
транзитивно, а `setup-msys2` затем удалил файлы из pacman cache. Команда
`pacman -S --needed` пропустила уже установленный пакет, поэтому копирование
архива завершилось ошибкой.

Вывод: `setup-msys2` не должен устанавливать UCRT64-зависимости до
восстановления кэша. Сведения о версии обновляются перед кэшем. Обновление
самого MSYS2 runtime выполняет `setup-msys2`: ручной `pacman -Syu` завершил
shell второго Windows job при смене runtime. Если пакет OpenSSL уже установлен,
его архив загружается через `pacman -Sw` для сохранения в Actions cache.

## 2026-10-16 — источник libcrypto для macOS

Гипотеза: готовый модуль macOS привязан к Homebrew OpenSSL.

Проверка: в модуле macOS ARM64 из выпуска № 7 команда чтения Mach-O
`LC_LOAD_DYLIB` показала
`/opt/homebrew/opt/openssl@3/lib/libcrypto.3.dylib`.

Вывод: системная криптобиблиотека macOS не заменяет этот OpenSSL; на
целевом ARM64 Mac нужна совместимая `libcrypto.3.dylib` по пути Homebrew
или перенастройка пути загрузки модуля. В Intel-архиве того же выпуска
подтверждён аналогичный путь `/usr/local/opt/openssl@3/lib/libcrypto.3.dylib`.

Владелец прямо попросил переписать коммиты с атрибуцией `mescheryakov1` на

После сбоя `imported-softokn` в Address Sanitizer владелец решил исключить
этот тест и удалить косвенные и сквозные тесты: они ему не нужны. Тестовый

## 2026-10-16 — расширение proxy-модуля p11-kit на macOS

Гипотеза: `proxy_module` из pkg-config всегда указывает на существующий файл.

Проверка: на macOS Intel установка p11-kit прошла, но `test -f` для пути из
`proxy_module` завершился ошибкой. Исходники p11-kit задают в pkg-config
суффикс `.so` для UNIX, а установочный скрипт создаёт ссылку на macOS-модуль
с фактическим расширением `.dylib`.

Вывод: при отсутствии указанного `.so` на macOS проверять соответствующий
`.dylib`, не меняя настройки других платформ.

## 2026-10-16 — модулю нужен драйвер PKCS #11 при проверке

Гипотеза: для smoke-теста достаточно только собранного провайдера OpenSSL.

Проверка: на Linux ARM64 GitHub runner сборка и оба unit-теста прошли, но
`openssl list -providers` завершился ошибкой `No PKCS#11 module specified`.
В локальной среде p11-kit задавал модуль по умолчанию, поэтому ошибка там не
проявилась.

Вывод: workflow должен установить p11-kit и явно указать его proxy-модуль
через `PKCS11_PROVIDER_MODULE` при проверке загрузки архива.

## 2026-10-16 — способ подключения готового провайдера

Гипотеза: другому проекту нужна библиотека `pkcs11-provider` для линковки.

Проверка: `src/meson.build` создаёт `shared_module`, а BUILD.md предлагает
скопировать модуль в каталог OpenSSL. Локальный проект, линкованный с
`libcrypto`, смог загрузить модуль из распакованного dev-архива через
`OSSL_PROVIDER_load`.

Вывод: архив предоставляет готовый модуль и заголовок интерфейса PKCS #11;
потребитель линкуется с OpenSSL, а модуль загружается во время работы.
